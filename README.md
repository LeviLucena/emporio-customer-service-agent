A text-based customer service agent for **Empório da Música**, a (fictional) musical instrument store in
Campo Grande/MS. It answers product, price, stock, order, returns and store-policy questions, grounded in the
store's CSV data and policy manual, and politely declines anything outside the store's scope.

* **Language:** Python (standard library only — no third-party dependencies)
* **LLM:** `gpt-oss:120b-cloud` served by [Ollama](https://ollama.com) (swappable via env var)
* **Approach:** function calling (tool use) with deterministic business logic in the tools
* **Interface:** interactive CLI with persisted history, plus a web chat UI (`web/`) backed by a small HTTP API

## Quick start

Requirements: Python 3.10+, and [Ollama](https://ollama.com/download) running locally.

```bash
# 1. Make the model available (gpt-oss:120b-cloud runs on Ollama's cloud; requires `ollama signin`)
ollama pull gpt-oss:120b-cloud

# 2. Run the agent (from the repository root)
python -m emporio_agent                              # interactive chat
python -m emporio_agent --session maria -v           # persist history in .sessions/maria.json, show tool calls
python -m emporio_agent --today 2026-02-20           # pin "today" (see "Dates" below)

# 3. Tests (no LLM needed, ~20 ms)
python -m unittest discover -s tests

# 4. Regenerate the example conversations (needs the LLM)
python scripts/generate_examples.py
```

Configuration (environment variables): `OLLAMA_MODEL` (default `gpt-oss:120b-cloud`),
`OLLAMA_HOST` (default `http://localhost:11434`). Any Ollama model with tool-calling support works,
e.g. `OLLAMA_MODEL=qwen3-coder:480b-cloud`.

### Web chat UI (optional)

A browser chat on top of the same agent. Run the API and the UI in two terminals:

```bash
# terminal 1 - agent API (stdlib http.server, no dependencies)
python -m emporio_agent.api --port 8000 --today 2026-02-20

# terminal 2 - React UI (Vite + React 19 + Tailwind 4); http://localhost:5173
cd web && bun install && bun run dev        # or: npm install && npm run dev
```

The UI shows which tool the agent used for each answer (the small green chips; hover to see the arguments),
renders bold/bullet formatting, and has a "New conversation" button. The backend URL is editable in the page header.
API contract: `GET /health`, `POST /chat {message, session_id?} -> {session_id, reply, tools_used[]}`,
`DELETE /chat/{session_id}`. Sessions are kept in memory (Redis/Postgres with a TTL in production).

CLI commands: `/novo` resets the conversation, `/sair` exits. Human handoff tickets are appended to
`handoffs.jsonl`.

## Architecture

```
 customer ──► CLI ──► Agent loop ──► Ollama (gpt-oss) ◄── system prompt (persona, rules)
                         │  ▲                 │ tool_calls
                         │  └── tool results ─┘
                         ▼
                      Toolbox ──► Repository (CSV in memory) · policies.md · Clock
```

| Module | Responsibility |
|---|---|
| `emporio_agent/data.py` | Loads/cleans CSVs, accent-insensitive search, promo & availability rules |
| `emporio_agent/tools.py` | 7 tools + JSON schemas; all arithmetic/date/policy logic is deterministic here |
| `emporio_agent/agent.py` | Tool-calling loop (max 6 rounds), history persistence, safe fallback reply |
| `emporio_agent/prompts.py` | Persona, grounding rules, scope and capability limits |
| `emporio_agent/llm.py` | Minimal Ollama `/api/chat` client with retries |
| `emporio_agent/api.py` | HTTP API (`/health`, `/chat`) consumed by the web UI |
| `web/` | Chat UI: Vite + React 19 + Tailwind 4 (single page, no router) |
| `knowledge/store_policies.md` | The policy PDF transcribed into topic-tagged sections |

### Tools

| Tool | Used for |
|---|---|
| `search_products` | Catalog queries, price ranges, categories |
| `get_product_details` | One product: price, promo, stock, specs, alternatives, expired promos |
| `get_payment_options` | PIX price, max interest-free installments (manual §3/§3.1) |
| `get_store_policy` | Hours (+ open-now), payment, returns, shipping, warranty, privacy… |
| `get_order_status` | Status/tracking — requires order number **and** matching e-mail/phone |
| `check_return_eligibility` | Regret (7d) / defect (30d) / preference (7d) windows with exact deadlines |
| `handoff_to_human` | Complaints and anything the agent cannot do; writes a ticket |

## Technical decisions and justification

**Function calling over RAG / text-to-SQL.** The corpus is tiny (65 products, 20 orders, an 8-page manual),
and most questions are *lookups with rules* ("is it in stock?", "can I still return order 7?"), not semantic
retrieval. Typed tools give exact answers and make the model's "when to consult data vs. policy" decision
explicit and observable (the tool trace). Text-to-SQL would add a failure mode (bad SQL, leaking other
customers' rows) for no benefit at this size.

**Policies: topic-routed sections instead of embeddings.** The manual is split into 10 topic-tagged
sections and fetched with an enum-typed tool. For a document this small, enum routing is deterministic and
cannot retrieve the wrong chunk. If the manual grew, I would add embeddings (`nomic-embed-text` is already
available in the local Ollama) behind the same tool signature.

**Deterministic logic outside the LLM.** Promo prices, PIX discount, installment limits, return deadlines and
"open now" are computed in Python. LLMs are unreliable at date/percentage arithmetic, and the manual
explicitly says wrong prices can be "propaganda enganosa".

**Model: `gpt-oss:120b-cloud` via Ollama.** Free, already available to me, strong tool-calling and good
Portuguese. The client is ~40 lines of `urllib`, so there is no SDK lock-in; changing provider means
implementing one method (`chat`).

**Prompt strategy.** One system prompt with: persona (informal-but-professional, as in manual §7.1),
"never state price/stock/policy without a tool result", explicit *can / cannot do* list, scope rules, and
WhatsApp formatting rules (no markdown tables). The date is injected on every turn. Language: replies in the
customer's language, Portuguese by default.

**Conversation persistence.** Optional `--session NAME` stores the full message list (including tool calls)
as JSON; resuming a session restores context. In production this would be keyed by WhatsApp number in a DB.

### Guardrails

* **Identity verification (LGPD):** order data is only returned when order number *and* the e-mail/phone on
  file match; "wrong owner" and "no such order" return the same message so order existence isn't leaked.
* **Scope:** accessories are redirected; off-topic requests (code, politics…) are refused even if mixed with
  a legitimate question or an "ignore previous instructions" attempt (see example 05).
* **No invented capabilities:** the agent cannot reserve items, take payments or cancel orders; it states so
  and points to the human team. Handoff is registered only after the customer confirms.
* **Transparency on promotions:** only `is_active=1` promotions are offered; if a customer mentions an ended
  one, the tool exposes it as *ended* so the agent can say so (manual §7.3).

## Data decisions and assumptions

The statement asks to document assumptions; these are the ones that matter.

| Finding in the data / manual | Decision |
|---|---|
| 25 promotions, only 4 with `is_active=1` | Only active ones are offered; several products have multiple expired campaigns — never quoted as offers |
| Multiple active promos on one product (not present now) | Non-cumulative (manual §6.2): the single best one is applied |
| Product 96 is `active` with `stock_quantity=0` | Treated as out of stock; alternatives suggested |
| Products 113, 136 `discontinued` | Not sellable; alternatives suggested |
| Product 130 is `coming_soon` **but** stock=2 and appears in orders 3 and 14 | Not sellable (status wins over stock); order history still shows it. Flagged as a data inconsistency |
| Categories 6–8 (sopros, metais, cordas) have **no products**, although the manual says the catalog has them | The agent says none are registered rather than inventing; offers human handoff |
| Orders 3 and 20: `total_brl` ≠ sum of items (3,450 vs 3,498; 1,400 vs 1,488) | Totals are reported as stored; likely discounts not modelled. Not corrected |
| No *delivery date* in the data, only `estimated_delivery` | **Receipt date = `estimated_delivery`** for the 7-day regret window; result is flagged `receipt_date_is_estimate`. Defect window (30d) counts from `order_date` as the manual states |
| Manual §3 table says min. installment R$100 for credit; §3.1 gives tiered minimums (R$50/80/100) | §3.1 is more specific, so it is used; "up to 3x: no minimum except below R$50" → installment must be ≥ R$50 |
| WhatsApp number (67) 3321-4500 (§7) differs from store phone (67) 3341-4444 (§1.2) | Both are reported as in the manual, each with its role |
| Regret right is for *online* purchases; orders have no channel field | Assumed all customer-service orders are remote purchases |
| Duplicate e-mail `bruno.martins@jmail.com` (customers 11 and 43) | Identity check accepts any matching record that actually owns the order, so neither customer is locked out and no other customer's order is exposed (regression-tested) |
| "Today" | Defaults to the real date. The dataset ends in March 2026, so with the real date every delivered order is out of the return windows; use `--today` / `Clock` to demo (the examples pin dates in February 2026) |

CSVs are UTF-8 and clean otherwise (no malformed JSON in `specs`); the `�` that may appear in some terminals
is a console encoding artefact, not a data problem (verified at byte level).

## Known limitations and what I would do with more time

* **LLM non-determinism.** Replies vary between runs. During development I found and fixed: the model sending
  `max_price=0` for "unset" (now ignored), recalling products from memory when a search was empty (prompt +
  tool note), writing code when asked inside an injection attempt, and calling the handoff before the customer
  confirmed. The regression tests cover the tool-side fixes; **prompt-side behaviour has no automated eval yet**.
  Next step: a small scripted eval set (like `scripts/generate_examples.py`) with assertions on tool calls
  and forbidden content, run on every prompt change.
* **Identity check is weak** (e-mail/phone known to the asker). Production should use the authenticated
  WhatsApp number or an OTP.
* **The agent cannot act**: returns/cancellations are *registered* for humans, not executed; no write access
  to orders or stock reservation.
* **Receipt date is estimated** (see above); holidays are not checked for "open now".
* **Search is lexical** with a tiny PT-BR stemmer: no synonyms ("violão de aço" vs "folk") or typo tolerance.
  Embeddings/fuzzy matching would fix it.
* **Stock is a snapshot** of the CSV; no concurrency or real-time inventory.
* **No streaming**; each turn waits for the full completion (typically a few seconds), in both CLI and UI.
* **The HTTP API is a demo server**: no authentication, open CORS, in-memory sessions.
* **Single store persona in Portuguese-first prompt**; multilingual replies work but were lightly tested.
* Minor model slips remain possible (e.g. calling a ukulele a "violão" in free text).

## Use of AI coding assistants

I used **Claude Code (Claude Sonnet 5.5)** as a pair-programmer in the terminal. My workflow:

1. **Read the brief and data first.** Claude extracted the challenge/policy PDFs and I reviewed the CSVs
   together with it to list data pitfalls *before* designing (the table above came out of that).
2. **Design decisions by me, typing by the assistant.** I chose the stack (Ollama + `gpt-oss:120b-cloud`) and
   the "deterministic tools" architecture; the assistant generated the modules, tests and this README draft.
3. **Verify with real runs, not vibes.** I ran the five scenarios against the actual model and read every
   transcript. That surfaced real bugs (listed in *Known limitations*) which were fixed with regression tests
   and prompt changes, then the examples were regenerated.
4. **Frontend from an existing design.** I pointed the assistant at my earlier repository so the UI reuses its
   design tokens and page logic; the assistant adapted it to this API and fixed rendering issues I reported
   (literal `**` markdown, scrollbar).
5. **Own the output.** Everything committed was reviewed; the policy transcription was checked against the PDF.
